# Backlog

Найденные баги и идеи, к которым нужно вернуться.

## 1. Чеки и история удалённого модуля остаются у нового модуля

Поставил сторонний модуль, написал в нём пару чеков, понял, что модуль плохой, и удалил его.
Потом переделал модуль, поставил другую версию, открыл новый сервис — там остались старые
чеки и история.

- Решить, правильное ли это поведение (переустановка той же версии vs другой модуль с тем же id).
- Выяснить, где хранятся чеки и история модуля и что с ними происходит при удалении модуля.

Сделано в 3.0.3 (вариант A): данные модуля хранятся по его id — консоли в каждой
сессии, история в `.console-history.sqlite3`, темплейты, hints и черновики Templates — и
намеренно сохранялись. Теперь подтверждение удаления в Settings имеет галочку «Delete them
too, in every session»: она удаляет консоли, чеки, ответы, историю, темплейты, hints и
черновики модуля во всех сессиях. По умолчанию данные по-прежнему сохраняются.

## 2. Источник модулей: папка или URL вместо одного архива

Пункты 2, 3 и 4 связаны (источник, обновление и версии внешних модулей) — делать вместе;
отложены.

Добавлять модуль архивом через Settings удобно, но лучше указывать папку или URL, где лежат
архивы модулей, и оттуда подгружать и обновлять кастомные модули.

- Варианты: папка (локальная, сетевой диск или git-клон; без сети и новых разрешений),
  URL на `modules.json` (id, версия, ссылка, sha256), GitHub-релизы (только публичные).
- Решить: обновление по кнопке с индикатором или автоматически; один источник или список;
  обновлять ли модуль, поставленный вручную, если в источнике версия новее.

## 3. Общие для команды конфиги (справочник, темплейты) и модули

Глобальные файлы (справочник, темплейты) нужно расшаривать с командой: я добавляю что-то
в свои файлы и пушу в общее хранилище, а остальные видят, что есть обновление.

- В Settings добавить место хранения этих файлов: папка или URL (git).
- Если хранилище под git — все могут пушить правки в общие конфиги и получать чужие обновления.
- Возможно, объединить с источником модулей (п. 2): у группы людей один репозиторий для этого
  приложения с модулями и конфигами.
- При открытии приложения показывать уведомление, что обновился такой-то файл; для конфигов —
  показывать diff и давать разрешать конфликты.
- Уведомления об изменениях файлов в native host — см. п. 8.

## 4. Установка второй версии того же модуля ломает список модулей

Если добавить две разные версии одного модуля, в Settings пропадают все модули, и непонятно,
что делать дальше.

- Ожидалось: ошибка «такой модуль уже установлен» либо проверка версии и обновление модуля.
- Нужно, чтобы список модулей не пропадал и было понятно, как восстановиться.
- Проверено: через native host `echo` 0.1.0, затем 0.2.0 (без `ui.wasm`) ставятся подряд,
  список не пропадает. Не воспроизведено; проверить с `ui.wasm` и через Settings. В
  `module_settings.rs` при ошибке загрузки списка строки молча очищаются — скорее всего,
  отсюда «пропадают все модули» без объяснения.

## 5. Ошибки в верхнем баннере вместо статусов

Сверху показывается баннер «Agent is waiting for one-time run approval in the Agent panel.
Dismiss». Такие сообщения должны быть в статусах.

- Найти все места, где сообщение выводится в верхний баннер.
- Верхний баннер — только для ошибок самого приложения, которые некуда вставить в статус.
- Всё остальное перенести в соответствующий статус (панели/инструмента) с debug-деталями.

Сделано в 3.0.3: локальные ошибки — в статусе владельца с debug, красным горит его
кнопка/вкладка/чек, увиденной считается, когда видна на экране (Agent: одобрение и ошибка
остановки — в панели Agent; автосохранение сессии — в статусе Sessions «Autosave»; Variables,
Modules, Templates, отображение ответа — в своих статусах). Глобальные ошибки (Import, Export,
Stop, Shift+Enter вне чека) остаются в баннере до Dismiss; Import/Export горят красным у
сервиса, где произошла ошибка.

## 6. STOMP-сервис для общения с Artemis

Добавить сервис (модуль) STOMP для работы с брокером Apache ActiveMQ Artemis: подключение,
отправка сообщений в очередь/топик и подписка на получение сообщений.

Сделано в 3.0.3: встроенный модуль `stomp` (STOMP 1.0–1.2, TCP и TLS). Чек:
`#endpoint` — `SEND|SUBSCRIBE stomp://user:pass@host:61613/destination`, `#headers` — заголовки
фрейма, `#options` — Count, Wait, Client-Id, Host, Columns-Type/Size, `#body` для SEND. SEND
ждёт RECEIPT брокера. SUBSCRIBE потребляет: подтверждает (ACK) каждое возвращённое сообщение,
по умолчанию `client-individual` + `consumer-window-size: 0` — брокер выдаёт по одному,
сообщения сверх Count остаются в очереди. Stop возвращает уже полученные сообщения. В Debug —
фреймы (пароль скрыт). Просмотр очереди без потребления (browse) не сделан.

## 7. Terminal: при ошибке не видно текста ошибки

Если команда в терминале завершается с ошибкой, показывается только статус-код 1, а самой
ошибки нет. Похоже, она уходит в stderr, но в Debug её тоже нет.

- Сохранять stderr команды и показывать его в статусе/Debug вместе с кодом выхода.

Причина: stderr не терялся — он показывается в ответе после stdout, но статус был только
`ERROR`/`WARNING`, а в Debug не было stderr; команда без вывода (`grep` без совпадений) давала
`ERROR` с пустым ответом. Сделано в 3.0.4: результат Terminal хранит последние 4 КиБ
stderr в `stderr` (видно в Debug); при ненулевом коде статус показывает `exit N` (или сигнал) и
последнюю строку stderr. Не изменено: код 1 — `ERROR`, другие ненулевые (например 127
«command not found») — `WARNING`.

## 8. Native host сообщает об изменениях общих файлов

Сейчас Dictionary и Variables перечитываются (`list`) при каждом открытии панели, потому что
native host не умеет сообщать об изменениях. Изменения из другого окна DevTools или ручная
правка файла видны только после повторного открытия панели.

- Каждое окно DevTools запускает свой процесс native host; общее у них только файлы
  `.dictionary-profiles.json` и `.variable-profiles.json`.
- Native host следит за файлами (FSEvents через `notify` или опрос mtime) и шлёт событие по
  долгой потоковой подписке `{service, op:"watch"}` — транспорт уже умеет потоки (Terminal,
  Splunk), протокол менять не нужно.
- UI обновляет панель без черновика; при несохранённой правке — «файл изменён в другом месте»
  с выбором версии. Свои записи не должны вызывать событие.
- Тогда можно убрать перечитывание при каждом открытии. Можно распространить на Templates и
  Hints. Связано с п. 3 (общие конфиги через папку/git с уведомлениями).

Уточнение: Variables (`var`) живут в сессии окна, общий файл только у Dictionary (и Templates).
Настоящая проблема была в том, что черновик Dictionary, начатый до сохранения в другом окне,
молча перезаписывал чужое сохранение. Выбрано без слежения за файлами. Сделано в
3.0.4: UI отправляет в `save` профиль, с которого начат черновик (`base`, хранится в
`servicesConsole.dictionaryDraftBases`); native отвечает CONFLICT, если профиль с тех пор
изменился (запросы без `base` — CLI и Agent — перезаписывают, как раньше). Черновик
сохраняется, кнопка **Discard draft** загружает сохранённую версию. Dictionary перечитывается
при возврате к панели DevTools и при фокусе окна. Слежение за файлами (watch) не делалось.

## 9. Ошибка считается «увиденной» слишком быстро

Ошибка в статусе открытой панели сразу считается увиденной, даже если была на экране 0,1 с.
Если переключиться на другую панель в момент ответа сервера, кнопка панели не загорится
красным, и ошибку легко пропустить.

- Считать ошибку увиденной, только если панель была открыта с ней хотя бы ~0,5 с
  (таймер в `rendered()`, отменяется при скрытии панели). Касается всех панелей с
  индикатором (Dictionary, Variables, Hints, Agent и т.д.).

Причина: `activity::Signal::observe` отмечал статус увиденным при первом рендере, когда он
виден. Сделано в 3.0.4: `observe` считает время на экране и отмечает увиденным после
`SEEN_AFTER_MS` (0,5 с); скрытый статус начинает отсчёт заново. Каждая панель (чеки, Hints,
Sessions, Settings, Variables/Dictionary, Templates, History, Agent) ставит один таймер
`SeenTimer` на ближайший срок и перерисовывается. Повторная загрузка Variables больше не
пересоздаёт статус той же ошибки черновика, поэтому увиденная ошибка не загорается снова.

## 10. Черновик Templates удалённого модуля ломает все черновики

Найдено по коду, не воспроизведено руками. Если удалить модуль (без удаления данных), пока
у него есть несохранённый черновик в Templates, то при следующем открытии панели Templates
показывает ошибку «Invalid Templates draft section» и отбрасывает все черновики
(`templates.rs`, `create()`: черновик проверяется через `has_template_section`, а модуль уже
не загружен). Следующая правка перезаписывает `servicesConsole.templateDrafts`, и черновики
других модулей теряются.

- Черновики незагруженных модулей не считать ошибкой: хранить, но не показывать, пока модуль
  не установлен снова (как консоли через `keep_unloaded`).

Причина подтверждена тестом: `create()` отбрасывал все черновики, если хоть один ключ не
относится к загруженному модулю/секции, а следующий `persist()` перезаписывал хранилище.
Сделано в 3.0.4: такие черновики хранятся как есть и не участвуют в проверке,
автосохранении и статусах (`loaded()` в `templates.rs`); после повторной установки модуля
работают снова. Ошибкой остаётся только ключ без `/`.

## 11. Что происходит с закрытыми чатами Agent

Проверить, что происходит с чатом Agent после закрытия: где он хранится, удаляется ли
(в сессии, в истории, у самого агента) и можно ли его вернуть.

- Не остаются ли после закрытия запущенные запросы, потоки и процессы агента.
- Не копятся ли данные закрытых чатов в хранилище без возможности их удалить.

Проверено по коду: закрытие останавливает идущий ход (`transport.stop` → native отменяет ход и
отключает SDK-сессию; после каждого хода сессия и так отключается), страничные инструменты
отзываются — ничего не остаётся запущенным. Но данные не удаляются и вернуть чат нельзя:
- в `localStorage` остаётся `servicesConsole.agentSession.<id>` (вся переписка и черновик), а id
  добавляется в `servicesConsole.agentClosedSessions`, который только растёт;
- native не удаляет `<data>/.agent/sessions/<id>/` (состояние и события Copilot SDK; на этой
  машине 16 папок, 15 МБ);
- UI для восстановления или удаления закрытых чатов нет. Переписка растёт в `localStorage`,
  общем с черновиками Templates/Dictionary, — при переполнении квоты начнут падать их записи.

Нужно решение: удалять при закрытии (возможно, с подтверждением) или вести список закрытых
чатов с «Восстановить»/«Удалить» и автоочисткой.

Выбрано: список закрытых чатов с «Восстановить» и «Удалить» (удаление чистит `localStorage` и
`<data>/.agent/sessions/<id>/`).

Сделано в 3.0.4: вкладка «Closed (N)» со списком (новые сверху), «Restore», «Delete» и «Delete all» с
подтверждением. Native-сервис `agent_sessions` (`list`/`delete`) сначала проверяет все id, не
трогает чаты, идущие в этом или другом подключении, и сообщает `deleted`/`removed`/`failed`;
UI удаляет записи браузера только для `deleted`. Ошибки — в статусе списка, с красным индикатором
кнопки, если не были увидены. Автоочистка не делалась.

## 12. Свои скилы для Agent

Придумать, как пользователь может добавлять свои скилы для агента, кроме встроенных
(`rust/native/agent-skills`).

- Где хранить: папка в Settings, вместе с модулем или в общем хранилище команды (см. п. 3).
- Как агент их находит и как пользователь видит, какие скилы подключены.

Сейчас: встроенный скил вшит в бинарь (`include_str!` в `native/src/agent.rs`), `SKILL.md` идёт в
системное сообщение, справочники — через инструмент `application_knowledge`. Copilot SDK
(1.0.26) умеет `skill_directories`/`disabled_skills` в конфиге сессии — стандартные папки
`<name>/SKILL.md`. Варианты (нужен выбор):
- папка `<data>/skills/` → `skill_directories`; в Settings список скилов, вкл/выкл
  (`disabled_skills`), установка из архива/папки как у модулей;
- скилы внутри пакета модуля (`skills/`), подключаются вместе с модулем;
- общая папка/URL команды (см. п. 3).

Выбрано: общая папка команды (связано с п. 3).

Сделано в 3.0.4: в Settings блок «Agent skills» с полем «Team skills folder» —
абсолютный локальный путь (git-клон или синхронизируемая папка), хранится в
`<data>/.agent/skills.json` (сервис `agent_skills` `get`/`save`). Settings показывает найденные
скилы и проблемы (нет `name`/`description`, выбрана папка одного скила). Каждый следующий ход
агента передаёт папку в SDK (`skill_directories` + `enable_skills` + инструмент
`builtin:skill`; в режиме `Empty` SDK по умолчанию скилы выключает). Личные
`~/.copilot/skills` не подключаются (проверено live-тестом). Использованные скилы видны как
активность «Skill: name» и в debug статуса. Ограничение: агенту доступен только текст
`SKILL.md`, файлов рядом он не читает. Загрузка по URL и синхронизация — в п. 3. Можно
откатить.

## 13. Подсвечивать правки Agent в сервисах

Когда агент меняет текст в консоли сервиса, изменённый фрагмент должен подсветиться примерно
на секунду и плавно погаснуть, чтобы пользователь видел, что именно сделал агент.

- Если вкладка сервиса не открыта, решить, показывать ли подсветку при переключении на неё.

## 14. Редкий сбой: гонка в stabby при первых вызовах REST/GraphQL

Примерно в 1 из 10 прогонов conformance-тестов процесс падает (abort) с паникой stabby-abi
72.1.16 `vtable/mod.rs:190` «VTable should've been inserted by now».

- Путь: модули с `Threads::Host` (REST, GraphQL) → `Served::spawn` → `transport::guarded` →
  создание `Dyn` при одновременных первых вызовах (discover).
- Причина: гонка в lock-free `AtomicArcBTreeSet` stabby (copy-on-write без безопасного
  освобождения памяти). Паника происходит вне `catch_unwind`, поэтому падает весь процесс;
  в рабочем режиме, вероятно, так же падает native host (не проверено).
- Варианты: заранее создать vtable при загрузке модуля или в `serve`; сериализовать первое
  создание `Dyn` (`Once`/`Mutex`); закрепить или пропатчить stabby (например,
  cfg `stabby_vtables="vec"`).

## 15. STOMP: просмотр очереди без потребления (browse)

Сейчас SUBSCRIBE потребляет сообщения: подтверждает (ACK) каждое полученное. Чтение без ACK не
делалось: растёт счётчик доставок (риск попасть в DLQ) и брокер можно завалить повторными
доставками.

- Идея: просмотр без потребления через управляющий API Artemis Jolokia (HTTP, `browse()` у
  MBean очереди), например метод `BROWSE` в модуле STOMP. Нужны URL консоли управления и
  учётные данные, это не порт STOMP.
- Заодно проверить: после Count-го ACK брокер выдаёт ещё одно сообщение, оно не
  подтверждается и возвращается в очередь при DISCONNECT. Растёт ли у него счётчик доставок,
  не проверено.

## 16. Agent не видит Debug проверок

Агент не может разобрать, почему упала проверка: у него нет доступа к Debug.

- `console_read_response` отдаёт только блок ответа в документе: строку `время · OUTCOME` и
  тело из `format::check_response`.
- `console_run_check` после своего запуска возвращает только строку `status` и текст
  `error`.
- Debug проверки (`run.debug` в UI: отправленный запрос, фаза ошибки, stderr Terminal, кадры
  STOMP, ответ транспорта и т. п.) не отдаёт ни один инструмент. Статус и Debug discovery
  тоже недоступны.
- Идея: инструмент `console_read_debug` (service, checkId, постранично) или Debug в ответах
  `console_run_check` и `console_read_response`. Нужно маскировать секреты (заголовки
  авторизации, пароли) и описать инструмент в скиле.
- Проверить, остаётся ли Debug после перезагрузки панели: сейчас он, похоже, хранится только
  в памяти UI.
